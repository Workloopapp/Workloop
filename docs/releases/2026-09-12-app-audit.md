# Workloop app audit — completed 12 September 2026

This audit began on 9 September and was completed on 12 September. It covers
the current local Flutter app and connected database/function contracts. It is
a findings report, not a claim that the fixes have been made or released.

Source: `/Users/ismaeelsmiley/Workloop`, version `1.0.0+19`, branch
`codex/comprehensive-launch-audit-2026-07-26`, base commit
`dbac1301674cc411a921db6a7828c3dc3c760738`, with substantial existing uncommitted
work. Source references below were rechecked on 12 September. No product code,
production data, schema, deployed functions or distribution settings were changed
by this audit. The hold on TestFlight uploads remains in place.

## Findings

P1 means fix before the next combined release because the defect can block a
core workflow or lose important information. P2 means a real correctness or UI
defect that should be addressed in the same repair pass. These are existing
workflow defects, not proposed new features.

### A01 · P1 · A payment-link failure can leave an invoice stuck

- **Trigger:** Create and issue an invoice with manually entered customer
  details and no saved client, then create a card payment link.
- **Actual:** The function reserves collection before unconditionally querying
  `contacts.id` with a null value. PostgREST emits `id=eq.null`, which is invalid
  for a UUID. No Stripe transaction is created, but the reservation remains.
  Recording a manual receipt or cancelling the invoice is then rejected as
  though a card payment were in progress.
- **Expected:** Valid manually addressed invoices can use the offered collection
  actions, and a failure before contacting Stripe does not strand the invoice.
- **Evidence:** On 9 September, the exact PostgREST client generated the null
  filter; an isolated replay of all 102 local migrations passed seven assertions
  proving issue, null contact, reservation, no transaction and both blocked
  recovery actions. On 12 September, read-only retrieval confirmed the same
  path in deployed Edge version 27 and the deployed reservation/guard functions.
  No merchant payment was attempted.
- **Location:** [Stripe receipt lookup](../../supabase/functions/stripe-payments/index.ts#L670)
  and its preceding collection reservation; document editor permits no client.
- **Repair:** Handle optional contacts using the invoice's authoritative saved
  customer details. Validate preconditions before reservation and give definite
  pre-Stripe failures a safe reservation recovery path.

### A02 · P1 · Accepted multiline text can prevent a PDF from opening

- **Trigger:** Paste a description with many short lines into an invoice or
  quote, then open its PDF. A 199-character description containing 100 short
  lines is within the editor's 300-character limit.
- **Actual:** The table row cannot span a page. An isolated copy of the current
  generator threw `PdfTooBigPageException` with assertions enabled and failed
  to complete until interrupted with assertions disabled. Normal content rendered.
  PDF creation runs through the viewer's loader on the UI isolate, so this is
  a potential app freeze, not just an unattractive page break.
- **Fresh evidence:** Repeated on 12 September: normal content generated 7,697
  bytes with and without assertions. The multiline case threw the page-limit
  exception with assertions and exceeded a bounded ten-second timeout without
  them. The harness changes only font loading to use local files. The freeze
  was not recreated on a physical iPhone.
- **Location:** [PDF table](../../lib/features/finance/documents/business_document_pdf.dart#L189),
  [accepted description](../../lib/features/finance/documents/document_editor_fields.dart#L100),
  [viewer loader](../../lib/shared/documents/workloop_document_viewer.dart#L106).
- **Repair:** Bound and paginate text safely, reject impossible layouts with an
  actionable message, and keep expensive generation from blocking interaction.

### A03 · P2 · Deposit and balance entries conflict in Money history

- **Trigger:** An invoice has two receipts in the displayed period, such as a
  £25 deposit and £75 balance.
- **Actual:** The timeline correctly creates two movements but the screen keys
  both rows with the invoice ID. A mounted Money screen raises `Duplicate keys
  found` for `income-invoice-one`; subsequent teardown can also fail because
  the element tree was interrupted.
- **Expected:** Each receipt or refund has its own stable row identity.
- **Location:** [PaymentCard key](../../lib/features/finance/finance_screen.dart#L736),
  [existing unique movement key](../../lib/features/finance/money_timeline.dart#L36).
- **Evidence limit:** Confirmed Flutter widget failure. Assertion behavior is
  different in profile/release; a production crash was not claimed or tested.
- **Repair:** Use the already-computed timeline entry key for each receipt row.

### A04 · P1 · Cancelling a booking deletes its existing notes

- **Trigger:** A booking contains access instructions or other notes. Cancel
  it and choose a reason, for example Weather.
- **Actual:** The reason replaces the complete notes field. Every confirmed
  cancellation through this screen supplies a reason.
- **Expected:** Retain the work notes and record the cancellation separately.
- **Location:** [status update](../../lib/features/appointments/appointment_detail_screen.dart#L352).
  The database already has `cancellation_reason` and `cancelled_at` in
  [the existing migration](../../supabase/migrations/20260715094933_add_booking_cancellation_metadata.sql).
- **Repair:** Use that existing cancellation metadata and preserve notes.

### A05 · P1 · Editing a booking's service leaves old details for invoicing

- **Trigger:** Edit a saved service booking, especially switching to another
  service at the same price.
- **Actual:** The update changes the booking title/service/price but leaves
  `appointment_items` untouched. The display model prefers the original item
  snapshot; the old name can reappear immediately after Save. Invoice creation
  can also reuse those old item descriptions when their total still matches.
- **Expected:** The booking, its displayed service details and a newly created
  invoice all describe the saved work consistently.
- **Location:** [booking update](../../lib/features/appointments/appointment_detail_screen.dart#L692),
  [snapshot read](../../lib/shared/models/slate_models.dart#L332),
  [invoice prefill](../../lib/features/finance/documents/business_document_editor_screen.dart#L176).
- **Repair:** Update the booking and its service-item snapshot together through
  the existing workflow, preserving any already-issued document history.

### A06 · P2 · Editing a task removes its booking link

- **Trigger:** Open a booking-linked task from Tasks, change its title or
  priority and save.
- **Actual:** The editor omits `appointmentId`; the repository explicitly writes
  `appointment_id: null`. The task stops appearing in the linked booking.
- **Location:** [task save](../../lib/features/tasks/tasks_screen.dart#L960),
  [repository update](../../lib/shared/repositories/tasks_repository.dart#L182).
- **Repair:** Preserve the existing booking relationship unless the owner
  explicitly changes it. Recheck the booking's task list after editing.

### A07 · P2 · Manual income and expenses can duplicate after a failed response

- **Trigger:** A new manual income entry or expense without a receipt commits
  on the server, but the response is lost. The owner follows the error message
  and saves again.
- **Actual:** Both paths issue a fresh insert with no stable creation identity.
  A mocked committed-but-lost response followed by retry produced two insert
  requests. This can double income or spending in the totals.
- **Location:** [income insert](../../lib/shared/repositories/payments_repository.dart#L224),
  [expense insert](../../lib/shared/repositories/expenses_repository.dart#L64),
  [no-receipt save branch](../../lib/features/finance/expense_editor_screen.dart#L191).
- **Repair:** Use one stable creation identity across retries, as the receipt
  expense and mileage workflows already do. This is not a double-tap issue.

### A08 · P2 · Expense load failures can silently become zero spending

- **Trigger:** The expenses endpoint returns an error whose message mentions
  `expenses`, including `permission denied for table expenses`.
- **Actual:** `_tableMissing` accepts any such message as a missing table and
  returns an empty list. A real repository plus mocked HTTP 403 reproduced a
  successful empty result. Money, dashboard-derived profit and tax reference
  figures can therefore show no expenses instead of a retry state.
- **Location:** [error classification](../../lib/shared/repositories/expenses_repository.dart#L156).
- **Repair:** Match only the exact supported missing-schema error; surface
  permission, query and service errors. Do not display financial zeroes for
  unavailable records.

### A09 · P2 · Onboarding accepts an invalid working day

- **Trigger:** Set Monday to open at 09:00 and close at 08:00, then Continue.
- **Actual:** The screen advances and stores the invalid draft without an inline
  error. Final onboarding validates that working hours are a JSON object, not
  that each enabled range is valid. Availability later rejects the reversed
  range, so the owner can save a day which offers no normal working interval.
- **Location:** [Continue](../../lib/features/onboarding/screens/ob_hours.dart#L70),
  completion function in
  [the current local migration](../../supabase/migrations/20260909082604_persist_onboarding_service_descriptions.sql).
- The Settings hours editor also saves without range validation; this needs
  the same shared fix rather than an onboarding-only guard.
- **Repair:** Reuse the working-hours range validator before advancing and at
  the completion boundary. Highlight the affected day while preserving entries.

### A10 · P2 · Invalid service prices are silently replaced

- **Trigger:** Paste malformed price text into Business → Services.
- **Actual:** Add parses with `double.tryParse(...) ?? 0`; edit falls back to
  the old price. The screen can report success for a free service or unchanged
  price without explaining that the entered value was invalid.
- **Expected:** Show a field error and keep the entered value available to fix.
- **Location:** Add and Edit price parsing in
  [settings_business_tab.dart](../../lib/features/settings/widgets/settings_business_tab.dart#L786)
  (Add line 786, Edit line 1000). Onboarding already rejects invalid service
  prices, so the same field behaves differently across entry points.
- **Repair:** Share the validated money input contract already used by the
  document editor, including a deliberate policy for zero-priced services.

### A11 · P2 · Future received-income dates distort current cash figures

- **Trigger:** Record income as received and choose tomorrow within this week
  or month. That date picker permits dates up to two years ahead.
- **Actual:** No save guard rejects the future received date. The current
  period's cash totals include it, while tax's recorded-income reference
  excludes future receipts. A £500 tomorrow receipt added £500 to today's
  current-week cash summary in the isolated calculation reproduction.
- **Location:** [received-date picker](../../lib/features/finance/add_payment_screen.dart#L213),
  [period sum](../../lib/shared/providers/finance_provider.dart#L137),
  [tax's different handling](../../lib/features/finance/tax_recorded_figures.dart#L26).
- **Repair:** Future dates belong to expected/due income; received income needs
  a consistent date guard and consistent handling of existing future records.

### A12 · P2 · Calendar export presents cancelled work as active events

- **Trigger:** Export a calendar containing a cancelled booking.
- **Actual:** The export includes a normal `VEVENT` without cancellation
  status. Importing that snapshot can make cancelled work appear scheduled.
- **Location:** [ICS construction](../../lib/shared/utils/calendar_export.dart#L6)
  and the calendar export screen's unfiltered appointment list.
- **Repair:** Define consistent snapshot semantics for cancelled bookings and
  either omit them or include the proper cancellation state. Verify updates
  against a previously imported event with the same UID.

## Additional verification risk · Task editor controller lifetime

- **Trigger:** Save an edited task and let its route close normally.
- **Actual:** The caller disposes the title controller as soon as the route's
  result future completes, while the outgoing editor can still rebuild during
  its reverse transition. The 9 September widget attempt observed
  `TextEditingController used after dispose` at the editor field.
- **Location:** [controller disposal](../../lib/features/tasks/tasks_screen.dart#L893)
  and [field](../../lib/features/tasks/tasks_screen.dart#L691).
- **Evidence limit:** The original widget run was disrupted by this exception;
  it is not evidence of an installed-phone crash. The lifetime mismatch remains
  in source. Give the editor ownership of its controllers until unmounting,
  consistent with the recently repaired onboarding service editor.

## What was checked without establishing a new defect

- The reviewed normal-size Light/Dark authentication, welcome, onboarding-hours
  and service-editor renders had no new clipping or mixed-palette problem.
  Aesthetic changes are not proposed merely to increase the findings count.
- The existing working-hours test at 320 × 568 with doubled text passed again
  on 12 September. Scrolling at accessibility text sizes is deliberate; no
  large-text layout defect was established there.
- Receipt capture, extraction review, account/workspace guards, document viewing
  and tax calculation paths were inspected. This did not substitute for fresh
  physical-device camera, OCR, sharing or accessibility testing.
- The 2026/27 tax bands, NI and mileage rates were checked against
  [HMRC Income Tax](https://www.gov.uk/income-tax-rates),
  [National Insurance](https://www.gov.uk/self-employed-national-insurance-rates)
  and [mileage guidance](https://www.gov.uk/simpler-income-tax-simplified-expenses/vehicles)
  on 9 September. No rate defect was established. The estimator's declared
  unsupported circumstances remain limitations, not newly discovered bugs.

## Live checks and evidence boundaries

Read-only production checks on **9 September, around 13:08–13:16 UTC** confirmed
the recent finance/recurrence migrations through `20260908200053`. The new
onboarding-description migration remains a deliberate local release dependency.
This report does not claim the 9 September provider snapshot is live on the 12th.

The database advisor returned six authenticated SECURITY DEFINER warnings and
26 private tables with RLS and no policies. Checked privileges showed no anon
execute for those six functions and no anon/authenticated DML grants on private
tables. These notices alone did not establish a vulnerability. This was not a
complete penetration test or fresh two-user hosted isolation run.

The sampled 24-hour cron runs succeeded and 384 retained worker HTTP responses
were 200. The seven-day push sample had one sent record and one intentionally
suppressed after its notification was read. There were no recent booking-email
or reminder rows in that sample; it therefore cannot prove new email delivery.

The earlier local baseline recorded 1,221 passing Flutter tests, ten existing
skips, clean analysis and a successful iOS profile build. That baseline missed
the cases above. The audit used focused reproductions; it did not rerun the
whole build matrix or treat the previous pass as evidence these workflows work.

Fresh 12 September evidence is retained in
[`build/product-audit-20260912`](../../build/product-audit-20260912):

- Four repository/calculation tests pass while asserting the observed defects:
  masked expense permission failure, non-idempotent income and expense retries,
  and future income included in current cash. These are reproduction checks,
  not tests demonstrating correct behavior.
- The actual Money screen regression fails with `Duplicate keys found` for the
  deposit/balance case. The failed result is expected until A03 is repaired.
- Bad-hours widget/RPC mapping reproduction and the existing small-screen
  doubled-text check: two tests passed.
- Two actual booking-screen reproductions pass observed-fault assertions:
  cancellation replaces existing notes, and changing to a same-price service
  retains the old item snapshot. Both completed without harness exceptions.
- PDF normal and multiline controls, plus read-only deployed Stripe source and
  reservation definitions, are saved with their results.

No fresh physical iPhone/Android journey, VoiceOver/TalkBack pass, real Stripe
collection/refund, external confirmation-email journey, or TestFlight dashboard
verification was completed in this audit. The current local changes and the
installed/uploaded build must be validated separately before release.
